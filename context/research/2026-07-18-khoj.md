## 1. Big picture (what khoj actually is)

A multi-user Django+Postgres(pgvector)+FastAPI hybrid server. Clients (Obsidian plugin, Electron desktop app, Emacs) push file contents over HTTP; the server chunks, hashes, embeds (local sentence-transformers on CPU by default), and stores chunks as pgvector rows. Chat is LLM-routed over that index. Automations are APScheduler cron jobs persisted in Postgres that re-enter the chat API and email results. It is exactly the "second server" our constraints say we don't want — but its ingestion/diffing/search-tuning decisions are directly transplantable to a small SQLite pipeline.

## 2. Content ingestion

**Core file:** `references/khoj/src/khoj/processor/content/text_to_entries.py` — abstract `TextToEntries` base every format inherits (`process(files: dict[path→content]) -> (num_added, num_deleted)`).

**Per-format processors** (each ~110–260 lines, all reduce a format to the same `Entry` shape):
- Markdown: `processor/content/markdown/markdown_to_entries.py` — recursive split on heading levels; each entry carries its **full heading ancestry** (`# file\n## H2\n### H3` prepended) so a chunk is self-describing; tracks `#line=` in a `file://path#line=N` URI for deep links.
- Org: `org_mode/org_to_entries.py` + custom 534-line parser `orgnode.py`.
- PDF: `pdf/pdf_to_entries.py` — PyMuPDF via langchain loader, one entry per page.
- Images: `images/image_to_entries.py` — **RapidOCR (rapidocr_onnxruntime, CPU ONNX)** extracts text; image becomes a plaintext entry. Cheap and effective for screenshots/photos of documents.
- Plaintext/docx/github/notion: siblings in the same dir.

**Entry schema** (in-memory: `utils/rawconfig.py` `Entry`; DB: `database/models/__init__.py` lines 768–813):
- `raw` (original chunk text), `compiled` (heading-ancestry-prefixed text that actually gets embedded — the load-bearing trick), `heading`, `file_path`, `file_source` (computer/github/notion), `file_type`, `uri` (`file://…#line=N`), `hashed_value` (**MD5 of `compiled`**), `corpus_id` (UUID grouping chunks split from one logical entry, used to dedupe results), `embeddings` (pgvector), FK to `FileObject` (full raw text of the source file).
- `EntryDates` side table: at index time a regex+dateparser pass (`search_filter/date_filter.py`) extracts every natural-language/structured date in the chunk into an indexed date column — this is what makes `dt>='last week'` filters instant without any LLM.

**Chunking:** split by heading structure first, then any entry > **256 whitespace-tokens** is re-split (paragraph > sentence > word priority), heading re-prepended to each continuation chunk, words > 500 chars dropped (URL/base64 junk defense).

**Incremental re-indexing — two-level change detection (the key design):**
1. **Client side, mtime:** Obsidian plugin (`interface/obsidian/src/utils.ts` lines 107–170) and desktop app (`interface/desktop/main.js` lines 193–256) keep a `lastSync` map (path → mtime) and only push files with newer mtime. **Deletion convention: a file pushed with empty content means "delete this file's entries."**
2. **Server side, content hash:** `text_to_entries.py::update_embeddings` (lines 142–263) — hash every current chunk, set-difference against stored `hashed_value`s per file: only new hashes get embedded; hashes present in DB but absent from the current parse are deleted. Editing one section of a big file re-embeds only the changed chunks. No mtime on the server at all — pure content addressing, so it's rename-tolerant and idempotent.

## 3. Search stack

**Models** (`processor/embeddings.py`, defaults in `models/__init__.py` `SearchModelConfig` lines 544–585):
- Bi-encoder: **`thenlper/gte-small`** — 33M params, 384-dim, ~70MB, sentence-transformers, normalized embeddings, loaded once at startup and kept warm. Comfortable on CPU: single-query encode is tens of ms; bulk doc encoding is the only slow part.
- Cross-encoder reranker: **`mixedbread-ai/mxbai-rerank-xsmall-v1`** — ~71M params; scores only the top-10 hits, ~100–300ms CPU per query. Rerank is **opt-in per query** (`rerank_and_sort_results` in `search_type/text_search.py`) — default path is bi-encoder only.
- Confidence gate: cosine-distance threshold **0.18** (`bi_encoder_confidence_threshold`) — below-relevance hits are discarded rather than padding context. Worth copying as a starting number.

**Store:** Postgres + **pgvector** (`database/adapters/__init__.py::search_with_embeddings` lines 2144–2172). No ANN index tuning visible — brute-force cosine over a personal corpus is fine, which validates doing the same with sqlite-vec or even numpy over tens of thousands of 384-dim rows.

**Hybrid?** Not BM25-hybrid. It's **vector search + deterministic pre-filters** parsed from query syntax (`search_filter/{word,file,date}_filter.py`, applied in `apply_filters` lines 2084–2110): `+"term"`/`-"term"` → SQL `icontains`, `file:"*.md"` → path filter, `dt>="last week"` → EntryDates range. Filters narrow the candidate set *before* the vector scan. Results deduped by `corpus_id`/hash (`text_search.py::collate_results`).

**Query flow:** query → strip/apply filters → embed query (warm model) → filtered cosine top-10 under 0.18 distance → optional cross-encoder rerank → dedupe → return `{entry, score, file, uri, heading}`.

## 4. Automations (scheduled NL tasks)

**Files:** `routers/api_automation.py` (CRUD), `routers/helpers.py` lines 2525–2700 (`scheduled_chat`, `schedule_automation`, `schedule_query`), `main.py` lines 150–182 (scheduler boot), prompts at `processor/conversation/prompts.py` lines 1033–1096 and 1214–1273.

- **NL → schedule:** one LLM call (`crontime_prompt`) turns "show me a quote every morning" into JSON `{crontime: "0 9 * * *", query: "...", subject: "..."}`. Guardrails are mechanical, post-LLM: truncate to 5 cron fields, `?`→`*`, **reject/randomize minute-level recurrence** (non-digit minute → random fixed minute to spread load), jitter=60s.
- **Storage/execution:** APScheduler `BackgroundScheduler` + `DjangoJobStore` (job metadata JSON stuffed into the job *name* field — hacky). `misfire_grace_time=60`, `coalesce=true`. Multi-worker leader election via a `ProcessLock` DB row. Job id = `automation_{user_uuid}_{md5(query+crontime)}` → duplicate automations are naturally idempotent.
- **Run:** the job re-enters the server's own **public chat HTTP API** with a service token — same brain path as interactive chat, exactly like our timers POSTing to the dispatcher. A "ran within last 6h" check suppresses double-fires.
- **The two genuinely novel ideas:**
  1. **`to_notify_or_not` (lines 1214–1252):** after the task runs, a second cheap LLM call decides *whether the result is worth notifying about* — "notify me when v2.0.0 is released" runs daily but only emails on the day it's true. Turns any recurring check into a condition-triggered alert.
  2. **`automation_format_prompt`:** separates *task execution* from *presentation* — a second pass reformats the raw answer as a readable report for the delivery channel.

**Vs. our systemd-timer + queue-dir:** ours is strictly better on the execution substrate (real cron semantics, `Persistent=`, journald, no second scheduler process — their in-memory-metadata hacks and 6h-double-fire guard are symptoms of app-level scheduling). What we lack is their **creation UX** (say a sentence to Jarvis → standing automation exists) and the **notify-or-not gate**. Both fit our architecture without APScheduler: schedules in a SQLite table, one generic `mission-automations.timer` (e.g. every 15 min, `Persistent=true`) asks the dispatcher "any due?" and enqueues matching tasks via the existing queue path.

## 5. Connectors

- **No calendar or email connectors exist in the khoj server** (grep for gmail/imap/caldav/icalendar returns nothing). Our Gmail-MCP plan is unaffected.
- **Notion:** `processor/content/notion/notion_to_entries.py` — page crawl, block-type whitelist, pages flattened to markdown-ish entries titled by ancestry.
- **GitHub:** `github/github_to_entries.py` — REST tree fetch of md/org/txt files, rate-limit sleep-and-retry, then reuses the markdown/org processors verbatim. Pattern worth noting: **connectors only fetch; normalization is always delegated to the per-format processors.**
- **File sync:** the client mtime+deletion-tombstone protocol in §2 is the real connector design worth studying.

## 7. Explicit SKIPs

- **The khoj server itself (Django + Postgres + pgvector + gunicorn)** — violates "no second server / SQLite-based"; multi-user auth, Stripe subscriptions, rate limiting, telemetry are dead weight for one maintainer.
- **APScheduler + DjangoJobStore + ProcessLock leader election** — app-level cron with metadata-in-job-name hacks; systemd timers already do this better. Lift only the *schema idea* (item 4).
- **Client apps** (obsidian/desktop/emacs/android/web) — we read files natively (locked decision #4); only their mtime/tombstone protocol informs item 1.
- **Conversation/chat engine, research mode, `/operator` browser automation** — Claude Code *is* our brain/agent runtime.
- **Email delivery via Resend, Twilio/WhatsApp** — cloud delivery; our channels are voice/dashboard/vault.
- **Image *generation*, speech modules** — cloud APIs; jarvis pipeline owns voice.
- **UserMemory / manage_memories** — LLM-extracts facts from chat history into an embedded memory table; chat-log-centric and Django-coupled; our vault-markdown memory covers it. Revisit as a prompt-level idea only.
- **Embedding-inference-endpoint indirection** (HuggingFace/OpenAI remote embeddings) — cloud path, contradicts CPU-only local.

## 8. Constraint check for our v2 ingest pipeline (what khoj validates)

- gte-small-class models (33M/384-dim) + a ~70M reranker are proven adequate for personal-corpus search on CPU — no GPU needed.
- Brute-force cosine over a personal corpus needs no ANN infrastructure — SQLite (sqlite-vec or a numpy sidecar) suffices.
- Content-hash chunk diffing makes re-index cost proportional to what changed — safe to run from a nightly (or 15-min) systemd timer.
- 256-token heading-ancestry chunks + a 0.18 cosine-distance cutoff are battle-tested starting hyperparameters.
