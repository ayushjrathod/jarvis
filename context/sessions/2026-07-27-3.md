# Session 23 — 2026-07-27: "open firefox" actually opens firefox

**User:** "when i say open firefox or any other installed app it should open it"

The parser was never the problem: `detect("open firefox")` had always returned
`Intent(launch, firefox)`, the policy had always been `allow`, and the journal
showed the verb running and reporting success — `desktop: ran launch -> Opening
firefox.` at 22:32 today, one of several. Nothing ever opened. **Three separate
bugs, in series**, each one hidden by the next.

## 1. The dispatcher has no display

`gtk-launch` ran with the dispatcher's environment, which contains no
`DISPLAY` and no `WAYLAND_DISPLAY` at all:

```
$ tr '\0' '\n' < /proc/$(systemctl --user show mission-dispatcher -p MainPID --value)/environ
DBUS_SESSION_BUS_ADDRESS=…  HOME=…  PATH=…  XDG_RUNTIME_DIR=…   # and nothing else
```

A systemd **user** service only carries the graphical variables if it started
*after* GNOME ran `systemctl --user import-environment`. At boot it doesn't.
The manager itself has them (`systemctl --user show-environment` → `DISPLAY=:0`,
`WAYLAND_DISPLAY=wayland-0`, `XAUTHORITY=…`); the service's snapshot predates
the import.

Reproduced exactly, with the service's env:

```
$ env -i HOME=… PATH=… XDG_RUNTIME_DIR=/run/user/1000 … gtk-launch firefox
exit=0
Error: no DISPLAY environment variable specified
```

**gtk-launch exits 0 regardless.** firefox printed that into a pipe nobody read
and died, and the verb cheerfully said "Opening firefox."

Fix: `desktop.session_env()` — our environment, plus any of `SESSION_VARS` it is
missing, taken from the systemd user manager. Asked at launch time, so it
survives a reboot; putting the variables in the unit file would not. Costs
nothing when the dispatcher *was* started inside a session (no variable missing
→ the manager is never queried). Clipboard verbs turn out to have worked all
along only by luck — `wl-paste` falls back to the `wayland-0` socket when the
variable is unset — so they now get the real values too.

## 2. With the app alive, a successful launch hung

First green run after fix 1: firefox opened **and** the verb answered
`Sorry — gtk-launch didn't respond.` `_run` uses `capture_output`, which waits
for EOF on the pipes; the launched app inherits them and holds them open for its
entire lifetime. So a **successful** launch blocked for the full 10s timeout
while a **failed** one returned instantly — the exact inverse of what you want,
and the reason bug 1 looked like a fast success for a month.

Fix: `desktop.spawn_app()` for GUI spawns — `Popen` with DEVNULL on all three
streams, `start_new_session=True`, and a short wait for the *launcher's* exit
code only.

## 3. The app would have died with the dispatcher

A child inherits our cgroup, so everything the dispatcher opened would sit in
`mission-dispatcher.service` and be killed by `systemctl --user restart
mission-dispatcher` — which this project does routinely. Checked the cgroup of a
gtk-launched app: glib does **not** move it to its own scope from here.

Fix: `spawn_app` wraps the launcher in
`systemd-run --user --scope --collect --quiet --slice=app.slice`, the mechanism
behind GNOME's own `app-*.scope` units. Returns in ~0.2s. Falls back to a plain
spawn if `systemd-run` is absent.

## No more false success

`gtk-launch`'s exit code says only that it forked, which is what let all of this
hide. `_launch` now checks for the process itself: `process_token(ident)` reads
the entry's `Exec=` and takes the binary basename, or the desktop id when the
Exec is a wrapper (`flatpak`, `snap`, `env`, `sh`, …) whose own name says
nothing. Nothing within `LAUNCH_SETTLE_S` (2s) → "firefox didn't start".

**The first live test of that check passed for the wrong reason** — matching the
whole command line found my own shell command, which merely contained the word
"firefox", and declared it already running. Matching is now against **argv[0]**
alone (whole-cmdline only for wrapper tokens, where the identity really is in
the later arguments). Verification is skipped when a match was already running:
a second launch only raises the existing window.

Also added: an explicit refusal ("I can't reach your desktop session") when
neither display variable can be found anywhere, on both `launch` and `open` —
better than spawning into the void.

## Live verification

Restarted `mission-dispatcher`, then through the real service:

| check | result |
|---|---|
| `POST /desktop {"command": "open firefox"}` | `Opening firefox.` — firefox running |
| its cgroup | `app.slice/run-p21360-i31345.scope` (its own, not ours) |
| `systemctl --user restart mission-dispatcher` | **firefox survived** |
| `POST /task` mode=auto, "open calculator" | desktop divert → running |
| same, "launch text editor" | desktop divert → running |
| same, "open photoshop" | `Sorry — I couldn't find an app called photoshop.` |
| module test under the service's stripped env | 6 variables borrowed from the manager, app opened |

Test instances closed afterwards. **432 tests green** (415 → 432): session env
merge + manager parsing, launch success/never-appeared/no-display/launcher-error,
`process_token` wrapper handling, `spawn_app` scope wrapping + DEVNULL. The
existing `TestOpenSchemeGuard` moved from stubbing `_run` to stubbing
`spawn_app`.

`scripts/doctor.sh` gained the check that would have caught this: whether the
systemd user manager has a display at all.
