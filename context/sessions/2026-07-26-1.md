## 2. Computer use — Phase K1 / tier T1 (commit `90d90dc`)

**Spike first, and it narrowed the tier `future/computer-use.md` assumed:**

- `org.gnome.Shell.Eval` → `(false, '')` — locked since GNOME 41.
- `Shell.Introspect.GetWindows` / `.GetRunningApplications` → **AccessDenied**.
  So **window list/focus/close is not reachable zero-dep** — needs a GNOME
  shell extension. Deferred, not built.
- Screen brightness: this gsd exposes only `.Power.Keyboard`, and
  `/sys/class/backlight/intel_backlight/brightness` is root-owned. Needs
  `brightnessctl` + udev. Deferred, not built.

Shipped `dispatcher/desktop.py` (sibling of `spotify.py`: pure `detect()` →
never-raises `run_intent()` → POST /task divert), zero new deps: status,
volume, mute, lock, launch, open, clipboard_get, clipboard_set. Volume phrasing
demands a system/master qualifier because `spotify.detect` owns bare
"volume 40" and its divert runs first.

Safety plane (doc §5, built with the tier):

- `computer.policy` allow/confirm/deny per verb, failing **closed**.
- Defaults are *not* "every write verb confirms" — these verbs are reversible,
  and confirming "system volume 40" by voice every time would be worse than no
  feature. `clipboard_get` and `open` confirm (passwords; exfiltration +
  injection payload).
- **`open` hard-restricts schemes at the executor.** `scheme_of` is hand-rolled
  because urlparse is actively wrong here: the dangerous schemes are *opaque*
  (no "//"), so prepending "//" to normalize a bare host made urlparse read
  `javascript:alert(1)` as a host with an empty scheme. **A test caught it
  passing the guard.** Regression pinned.
- Confirmations park in-memory (120s), fire an SSE `confirm` event, and are
  answerable from the new `ConfirmBar` banner above the dashboard grid **or by
  a bare "yeah"/"nope" by voice** — only when that same source has one pending,
  so a stray "yes" routes normally. Ids single-use.

Seams: `POST /desktop`, `POST /desktop/confirm`, `GET /desktop/verbs`. Docs
page gained a "Media & desktop" group (the media routes were never documented
either). Deliberately **not** an area — an area would need Bash to reach the
session bus, exactly what `security.privileged_areas` prevents.

## 3a. Degraded mode when the plan cap hits (commit `aee97a6`)

The plan-wide cap killed the assistant twice (sessions 7, 10). `offline.py` now
answers from the Phase F/J hybrid index instead — **extractive only**: verbatim
quotes with the source file named, no generation.

**The relevance anchor is the load-bearing part, and live testing found it.**
KNN always returns something: asked "the airspeed velocity of a laden swallow",
the index handed back its three least-unrelated chunks, which then got quoted
under "here's what I already have on it". A degraded answer is now only offered
when BM25 matched a real term first; ranking still uses the hybrid path.
Also strips `<!-- -->` comments (USER.md/MEMORY.md open with an editor
instruction that otherwise ate the whole quote).

Run still settles `failed` (honest cost/latency stats); the done payload
carries `degraded: true`. Config `memory.offline_fallback`. This is the seam a
local model would plug into later — that needs a dep + a user decision, this
needed neither.

## 3b. Event-driven proactivity — inbox watcher (commit `56d41bb`)

First non-clock trigger in the system. `dispatcher/inbox.py` polls
`vault/inbox/`; a file fires once its (mtime, size) is stable across two polls
(so a half-written PDF isn't indexed short), first pass seeds without firing.
`step()` returns **(arrived, removed)** — the removed half exists because live
testing showed a deleted file stayed searchable until the next restart.
Deterministic by default (reindex + "Indexed X — searchable now");
`inbox.summarize` is opt-in.

## 3c. Approval queue — NOT built, deliberately

The third listed gap. The **surface** now exists and is reusable (SSE
`confirm` + dashboard banner + voice yes/no + timeout + single-use ids, built
for desktop verbs above). But there is **nothing outbound to gate**: Gmail is
read-only and not even OAuthed, and no send/write-to-the-world capability
exists anywhere in the system. Building a queue for hypothetical actions would
be speculative. Recommendation: wire the existing confirm plane to the first
real outbound action when one lands (most likely Gmail send after OAuth).
