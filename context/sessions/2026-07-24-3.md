# Session 2026-07-24 (3) — "talk to Jarvis" voice button on the dashboard

Follow-on to session 18 (phone access over Tailscale HTTPS). The user wanted a
button on the **main dashboard** (not the /ask page) that turns the browser into
the same voice loop as "hey jarvis": click to start listening, click the same
button again to stop, then transcribe → ask Jarvis → stream the answer → speak
it aloud. Primarily for phone use over the Tailscale Serve URL.

## Key constraint (why browser-side, not the server mic)

"hey jarvis" (`jarvis/main.py`) records the **Arch box's** microphone via
sounddevice — a browser button, especially on a phone, cannot use that mic. So
the browser captures its own audio (`getUserMedia` + `MediaRecorder`) and POSTs
it to `/stt`, exactly like `ui/src/AskScreen.jsx` already does. There is **no
server `/tts` endpoint**, so the reply is spoken with the Web Speech API
(`window.speechSynthesis`) — free, no server, works on phones.

## What I changed (UI only — no Python touched)

- **`ui/src/widgets/CommandBox.jsx`** — the widget already was "the typed
  equivalent of talking to Jarvis". Added:
  - A mic toggle button between the input and Send. Click → `getUserMedia` +
    `MediaRecorder` starts (state `recording`, label "◼ listening…", red via
    `.mic.recording`); click again → `rec.stop()`; `onstop` blobs the chunks,
    POSTs to `/stt` (state `transcribing`, "…"), and auto-submits the heard text.
  - Refactored the submit path into `runTask(q, {speak, source})` shared by typed
    Send (`speak:false`, source `ui`) and voice (`speak:true`, source
    **`ui-voice`** so voice follow-ups resume their own CLI session, kept apart
    from the on-device `voice` source). Uses `postTask` with default `mode`
    (auto) — same routing as the voice path (quick/agentic + media/automations
    diverts).
  - `say()` speaks the final streamed answer (or the agentic ack / error) via a
    fresh `SpeechSynthesisUtterance`, feature-detected (`"speechSynthesis" in
    window`), best-effort try/catch, `speechSynthesis.cancel()` before each new
    task so a new question interrupts the last reply. A **"mute reply"** checkbox
    (shown only when speech is available) suppresses it.
  - The spoken question echoes back as a `you: …` line; errors (getUserMedia
    denial, `/stt` non-200, empty transcript) become visible notes — the widget
    never crashes, matching AskScreen/CommandBox error handling.
- **`ui/src/styles.css`** — the `.mic` styles were scoped under `.ask-input`;
  added dashboard-scoped `.command-form button.mic` (outlined, `min-width`/pad so
  it's tap-sized on a phone), `.command-form button.mic.recording` (red), plus
  `.command-tools` / `.mute-toggle` / `.asked`.

No new deps, no dispatcher/API change (`/stt` + `/task` already exist and are
already dev-proxied in `ui/vite.config.js`). `jarvis/*.py` untouched.

## User-side / caveats

- **Grant mic permission** the first time the browser asks. On the phone the mic
  needs a secure context — the Tailscale Serve URL is HTTPS, so it works;
  plain-http loopback (127.0.0.1) is also a secure context.
- **iOS Safari** can throttle `speechSynthesis` started from async code (after
  the fetch resolves) and may need a voice loaded first; speaking is best-effort
  and never blocks the UI. If silent on iOS, the "mute reply" box unchecked +
  a manual re-tap usually warms it. Android Chrome speaks fine.
- Behavior to try: open the dashboard, tap 🎤 ("Talk to Jarvis"), speak, tap ◼
  to stop → the answer streams into the widget and is read aloud.
