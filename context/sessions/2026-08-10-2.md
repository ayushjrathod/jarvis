# Session 29 — 2026-08-10 (2): system volume control, widened

User: "i want you to add system volume control."

## It was already there — what was missing was reach

System volume control shipped with computer-use T1 (`dispatcher/desktop.py`,
session 20, K1 in the phase tracker): verbs `volume` / `mute` / `status` over
`wpctl`, policy `allow`, live and enabled in `config.yaml`. So the request as
literally stated was already satisfied, and I said so before touching anything.

What made it *feel* missing is that the parser only recognised four shapes.
Exercised against both parsers at session start:

| parses today | falls through to a model |
|---|---|
| `system volume 40` | `turn up the system volume` |
| `set the system volume to 40` | `raise / increase / lower the system volume` |
| `system volume up` / `down` | `volume up on my computer` |
| `turn the system volume up` | `mute my computer`, `max volume`, `half volume` |

Every miss is a real `claude -p` call — ~$0.10-0.14 notional and ~3s TTFT to do
what wpctl does instantly for nothing. That is the same waste the brief
quiet-day check (session 25) and the meta-task routing (session 20) exist to
avoid, so widening the parser is squarely in that family.

I offered four options (widen phrasings / dashboard slider widget / give the
system the bare verbs / do nothing). **User chose: widen the phrasings.** The
other three were not built.

## The invariant that shaped the work

`spotify.detect` runs first in the divert chain and owns the **unqualified**
volume vocabulary — `volume 40`, `louder`, `turn it up`, bare `mute`/`unmute`.
The desktop module's rule has always been that every one of its volume patterns
must carry an explicit system/master/computer qualifier, or the two parsers
fight over the same sentence.

So the widening covers only qualified phrasings, and **deliberately still
leaves `max volume`, `half volume` and `make it louder` to route normally**.
Claiming those here while bare `volume 40` goes to Spotify would split one
sentence shape across two subsystems — exactly the confusion the rule prevents.
Flipping that precedence was option 3, and it's a separate decision.

## Changed — `dispatcher/desktop.py` (parser only)

- `_SYS` gained `machine|pc|speakers?`; new `_DET` (`the|my|this`), `_AUDIO`
  (`audio|sound`, system-side words that have always been taken unqualified by
  the mute patterns) and `_NOUN` (`volume|audio|sound`).
- **`NAMED_LEVELS`** — max/maximum/full/full blast/all the way up → 1.0,
  half/halfway → 0.5, (a) quarter → 0.25, min/minimum/zero/silent/all the way
  down → 0.0. Absolute, so `_set_volume` clamps to 1.0: "max" is 100%, not the
  150% boost wpctl would allow.
- **Absolute**: `_VOL_SET_RE` (now takes set/put/change/turn + a determiner +
  a named *or* numeric value), `_VOL_SET_ON_RE` for the trailing-qualifier form
  ("set the volume to 40 on my computer"), `_VOL_MAX_RE` ("max out the …").
- **Relative**: `_VOL_REL_RES`, five patterns split by sentence shape rather
  than one mega-alternation — a *leading* direction word is a verb (raise,
  increase, boost, lower, decrease, reduce, drop) and a *trailing* one is an
  adverb (up, down, louder, quieter, softer), and they want different slots.
  `_DOWN_WORDS` decides sign.
- **Mute**: `_MUTE_RE` takes a determiner ("mute **my** computer"), plus
  `_SILENCE_RE` and `_SOUND_TOGGLE_RE` ("turn the sound off", "turn off the
  system audio"). The toggle is restricted to audio/sound on purpose — "turn
  the volume off" would be a bare-volume phrasing.
- **Status**: "is the system muted", "how loud is the computer", "what volume
  is the system at", "what's **my** system volume". These sit above the
  question-mark veto (read verbs *are* questions), so the "?" forms work.
- `_level_of()` — shared value extraction. Above 100 still returns None from
  `detect()` entirely rather than clamping: "system volume 400" is far likelier
  to be a misheard sentence than an intent to deafen you, so it routes normally.

`_VOL_WORD_RE` is gone, replaced by `_VOL_REL_RES`. No executor, service, or
config change — `Intent` shapes are unchanged, so everything downstream
(policy plane, confirm flow, divert, SSE) is untouched.

## Tests — 721 → 728, green

`tests/test_desktop.py` +7: relative phrasings (both directions), absolute

# Addendum — 2026-08-11: subagent review of the above, and its fixes

User asked for a subagent code review of the change. It verified by execution
(combinatorial grammar expansion, per-word mutation testing, replay of 244 real
historical `tasks.text` rows, HEAD-vs-working-tree differential) rather than by
reading, which is why it found things I had not. **728 → 732 tests.**

## Three real defects, all mine, all fixed

**1. `machine state` executed as a status command** (`desktop.py` `_STATUS_RE`).
Adding `machine|pc|speakers?` to `_SYS` widened the bare
"<qualifier> status|state" alternative along with everything else:

```
'machine state' / 'the machine state' / 'my machine state'
'what is the machine state?' / 'pc status' / 'speaker state'   -> Intent(status)
```

Status is matched *before* the `?` veto (read verbs are questions), so the
interrogative form was claimed too. A developer asking about a state machine, a
VM or a CI box would have got "system volume 16%, screen unlocked", filed
`done`, never reaching a model. Exactly the family of "open the door" → launch
an app called "the door".

Fix: split the qualifier in two. `_SYS_CORE` (system|master|computer|desktop|
laptop — the words that were always in that shape) for the bare status form;
the wider `_SYS` only where an audio noun or the lock disambiguates it.

**2. My negative test pinned nothing — and both STATE.md and CLAUDE.md said it
did.** `test_ordinary_english_is_not_a_volume_command` was written to prove the
system qualifier is load-bearing. It doesn't: none of its six inputs ("raise an
exception", "lower my expectations", …) contains an audio noun, so they are
rejected on the noun whether or not the qualifier is required. The reviewer
proved it by mutation — making the qualifier optional leaks

```
'raise the volume' -> +10%    'lower the sound' -> -10%    'turn up the volume' -> +10%
```

and that test **still passed**. Only the older `test_bare_volume_is_left_to_
spotify` caught it.

Fix: `test_the_system_qualifier_is_what_keeps_them_apart` — same shape, but
every input carries an audio noun and no system word, so it can only fail for
the reason claimed. I re-ran the mutation myself to confirm it now fails (my
first attempt at the mutation was malformed — it produced a double space and
leaked nothing, a reminder that a mutation test that "passes" is meaningless
until you check the mutant actually changed behavior).

**Generalizable**: a negative test proves nothing unless its inputs can *only*
fail for the reason being asserted.

**3. Coverage gap in the exact thing the change existed to fix.** The trailing-
qualifier relative form required the noun *before* the direction word, and the
absolute trailing form only took numbers, so the whole `_VERB` vocabulary and
`turn up … on …` were unreachable:

```
'turn up the volume on my computer'   'raise the volume on my pc'
'lower the volume on the laptop'      'crank up the system volume'
'put the system volume up'            "turn up my computer's volume"
'mute the computer please'
```

— all still a ~$0.10-0.14 `claude -p`. Fixed with two more patterns
(`_VOL_REL_RES[5]`/`[6]`), `_HOIST` (turn|crank|bump|kick|dial), "put … up",
`_SYSP` for the possessive, and a **trailing** "please" strip in `_normalize`,
which had only ever stripped the leading form.

## Hardening the reviewer asked for

`_DOWN_WORDS` is a denylist — `dir not in _DOWN_WORDS ⇒ louder` — so a word
added to `_VERB`/`_ADV` and forgotten there silently turns the volume **up**,
on a verb whose policy is `allow` (no confirmation, nothing to notice). Its
mutation run showed `drop` and `softer` were killed by **no test at all**. Now
`_UP_WORDS` exists and `test_every_direction_word_is_classified` pins the
partition.

Plus, from its nitpicks: `_level_of` had zero blank lines before `_LOCK_RE`
(read as part of the function body); `test_nonsense_volume_rejected` never
touched the trailing-qualifier path or the 100/101 boundary; and
`test_bare_volume_is_left_to_spotify` asserted only that desktop declines those
strings, never that spotify *claims* them — which is the half of the invariant
the comment is actually about. All three closed.

- Mutation re-run: qualifier-optional now fails 2 tests (was 0).
- Direction-word partition holds.
- Unqualified forms still unclaimed: `max volume`, `half volume`, `make it

- `parse_answer` unaffected by the politeness strip ("no thanks" → False,

# Part 3 — 2026-08-11: the standing list, three items

User picked: commit the volume work, fix the voice-unit restart loop, sweep the

## 1. Both voice units could flap forever without ever failing

`mission-jarvis` and `mission-dictate` carried `Restart=on-failure` +
`RestartSec=5` and no StartLimit. systemd's default is 5 starts per **10s**, so
at a 5s pace only ~2 restarts land in the window: the limit can never trip, and
a crash-on-startup (no mic, models missing, ydotoold down, user not in `input`)
loops forever reporting **"activating"**, never `failed`. Session 28 diagnosed
and fixed precisely this on the dispatcher and missed these two — where it
matters more, because nothing else surfaces it: Jarvis simply stops answering.

Both now mirror the dispatcher: `StartLimitIntervalSec=300`,
`StartLimitBurst=5`, `RestartSec=10` — five starts in ~40s, comfortably inside
the window, so it gives up where `systemctl status` and doctor.sh can see it.
Installed and `daemon-reload`ed; **neither service needed restarting** —
systemd re-reads the unit on reload, confirmed live (`RestartUSec=10s`,
`StartLimitBurst=5`, `StartLimitInterval=5min`, both still active).

New `TestSystemdUnits.test_every_restarting_unit_can_actually_give_up` checks
every `Restart=`-bearing unit has both StartLimit keys **and** that
`burst * RestartSec < interval` — the pacing is the load-bearing half, and this
mistake has now been made twice.

## 2. `graph_extracted_at` — the graph tracks its own hand-off

`/memory/consolidate` marks a batch consolidated and spawns *both* the
consolidation agent and graph extraction over it. Session 28's M6 rollback
returns episodes to the pool when the **consolidation** fails — which hands the
extractor, next pass, episodes it already digested successfully. The only thing
preventing duplicate facts was `add_fact`'s exact-duplicate rejection, i.e. a
guard doing a design's job.

- `episodes.graph_extracted_at` (additive migration, NULL = never extracted).
- `db.episodes_needing_graph(ids)` / `db.mark_episodes_graph_extracted(ids)`.
- `memory.render_episodes()` extracted from `build_consolidation`, so the graph
  can be handed a **different subset** than the consolidation export holds.
- `_consolidate` filters to the pending subset and renders that; nothing to do
  logs "nothing new in this batch".
- Marked **only on the success path** in `Service.graph_extract`, so a parse
  failure or a rate-limited run is retried next pass — the same
  fail-toward-retry direction the consolidation half takes.

Applied to the live DB on restart: column present, `integrity_check` ok, 82
episodes / 4 unconsolidated intact. (DB copied to the scratchpad first.)

## 3. `ConfirmBar` expires client-side

A parked confirmation lives `confirm_timeout_s` (120s) in the dispatcher and is
then dropped; a dispatcher restart drops every pending intent. The banner knew
neither, so it kept offering **Yes** on an id the server had already forgotten —
click it and you got "that confirmation expired", with nothing beforehand. On
the two verbs the confirm plane exists to guard (`clipboard_get`, `open`), a
silently-stale Yes button is the one thing that UI must not offer.

The `confirm` SSE event now carries `timeout_s`; each row stores its own
deadline, one interval drives the countdown (and stops when nothing is
pending), and expired rows remove themselves.

**Browser-verified**, because unit tests can't see a timer render. chromium +
CDP against an **isolated** dispatcher on :8799 with its own DB and
`confirm_timeout_s: 8`:

```

...
t+7s  bar=true   ttl=1s  yes=true
t+8s  bar=false  ttl=null yes=false
```

The clipboard was never read — the point was to watch it expire. The real
dispatcher on :8765 and `data/mission.db` were never touched.

## Two environment gotchas worth remembering

- **`pkill -f "remote-debugging-port=9222"` kills the shell issuing it** — the
  pattern matches that shell's own command line. Cost one confusing exit-144.
- **An isolated dispatcher's config must live in the repo root.**
  `Config.root` is the config file's parent, so a config in /tmp makes
  `ui/dist` unreachable: `/` serves the API JSON instead of the SPA and every
  DOM assertion fails for a reason that looks nothing like the cause.

## A correction the DB forced

STATE.md (session 25) said the learning loop was dormant — "2 reflections ever,
last 07-19". The database says **4, most recent 2026-08-09**. It is not dead,
just rare: 5 of 83 agentic runs ever (6%) clear `reflection_min_turns: 12`,
because the daily brief lands at 8-11 turns and sat one turn under the bar.

Reflection cost is also **higher than CLAUDE.md claims** ($0.108). The last
three real ones: $0.1967, $0.2283, $0.2065 — call it $0.21.

## Lowering the trigger changed shape once measured

| threshold | runs qualifying (of 83) |
|---|---|
| 12 (was) | 5 (6%) |
| 10 | 15 (18%) |
| 9 | 23 (28%) |
| **8 (now)** | **34 (41%)** |

But 8 is exactly where the daily brief lives, so a naive change would spawn a
~$0.21 review of "I wrote today's brief" **every single day**, almost always
concluding there is nothing to save. That is the same mistake `should_capture`
made with episodes until 2026-08-02, when daily-brief runs were left in and the
knowledge graph filled with the system observing itself.

So the change is two-part:

- `reflection_min_turns: 12 → 8`.
- `learning.no_reflect_extra: [daily-brief, weekly-review]`, applied **on top
  of** the hard-coded `NO_REFLECT_TASK_TYPES`. Config can widen the exclusion
  but never narrow it past the recursion guard — `reflection` itself must stay
  excluded or the loop reflects on its own reflections. Same fail-closed shape
  as the desktop policy plane. Delete the config key to reflect on the timer
  agents again.

Verified against the real config: daily-brief/weekly-review/reflection → False,
an ordinary `summarize` or an untyped task at 10 turns → True. +2 tests.
