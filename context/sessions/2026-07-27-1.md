## 1. The Messages API backend was missing three things (commit `ce93ea0`)

It had **never executed on this machine**, so it was shipped untested.
Comparing signatures made the gap concrete —
`_stream_api(text, cfg, model_override)` versus
`_stream_cli(text, cfg, model_override, tools, context, resume_session_id,
procs, task_id)`. Switching backends would have silently dropped:

1. **Memory blocks** — `context` wasn't even a parameter, so locked decision
   #4 (blocks in every quick prompt) would have been lost. Now folded into the
   system prompt.
2. **Conversation continuity** — the API is stateless. `quick.HistoryStore` is
   the equivalent of the CLI's `--resume` transcript, and deliberately mints
   and returns a `session_id` so `quick_sessions` and
   `metadata.resume_session_id` in service.py work **unchanged** on both
   backends — nothing above `quick.stream` learns a new shape. Bounded per
   session (`budgets.quick_history_turns`, 6) and LRU-capped across sessions,
   because every turn is re-sent as input tokens. Refusals are never recorded
   (replaying one would poison the thread).
3. **Barge-in** — `quick.ApiAbort` duck-types the two attributes
   `Service.cancel`/`shutdown` touch (`returncode`, `kill()`), so locked
   decision #7 holds on both backends with no change to either caller.

Also **pooled the client per event loop** (`quick.api_client`, released in
`Service.shutdown`): a fresh `AsyncAnthropic` per turn meant a fresh TLS
handshake per voice question — measured 1826ms first call vs 1526ms steady
state, so ~300ms of the TTFT.

## 2. Measured, and one earlier prediction was wrong

|---|---|---|
| cost | **$0.00051** | $0.14052 |

## 3. Two traps, both found by testing with the real key

- **The key has no credit** (the first smoke run spent the last of it). Since
  `auto` routes to the API the instant the env var exists, wiring `.env` in
  would have made **every** quick question 400. Fix: a request that fails
  **before emitting any delta** with a billing/auth error falls through to the
  CLI transparently, and `disable_api()` puts the API on a 15-minute cooldown
  so a dud key costs one round-trip per window instead of one per question.
  Mid-stream failures still raise — half the answer is already spoken and
  restarting would repeat it.
- **Worse: the CLI prefers the key over the claude.ai login.** It says so —
  "claude.ai connectors are disabled because ANTHROPIC_API_KEY … takes
  precedence over your claude.ai login". So an exported key *replaces* the
  subscription, and the fallback above was landing on a CLI that was itself
  broken. `runner.cli_env` now strips `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`
  from **every** `claude` subprocess, quick and agentic. With a funded key this
  would also have silently billed CLI runs to API credit at ~18k system-prompt
  tokens each.

End to end with the unfunded key exported: API 400 → CLI fallback → correct
answer from the memory blocks; second question skips the doomed call entirely
(3.7s vs 6.4s).

### The doctor check earned itself immediately

`mission-tailscale-serve` had been **dead for a day**. At boot it ran while
tailscaled was still in `NoState`, exited 1, and as a `oneshot` with no restart
it stayed down. `After=tailscaled.service` orders against the unit *starting*,
not against the daemon being *ready* — the same shape as the session-8 race
where a timer fired before the dispatcher had bound its port. Fixed with an
`ExecStartPre` that waits up to 60s for `BackendState: Running`.

Phone access had kept working the whole time (verified: tailnet `/health` →
200) because `serve --bg` persists the mapping in **tailscaled's own state**,
not in the unit. The real exposure was a fresh boot after a state reset.
